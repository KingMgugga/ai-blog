Skills from plugged-in tools, tighter OpenAI limits, and agents that wait for approval

Today's Claude Code update lets connected tools bring their own skills, OpenAI reportedly tightens limits, and T3 Code adds scheduled agent workflows with sign-off steps.

What matters today

  1. claude-code 2.1.332

    Claude Code 2.1.332 can now load skills (saved instructions that teach the assistant a specific job) directly from MCP servers. MCP stands for Model Context Protocol, a standard way to plug outside tools into an AI assistant, and this feature is in beta. The update also adds a hook, a check that runs automatically before an action, which can block shell commands written inline inside skills. It adds new OpenTelemetry events too, which means more usage and activity data you can send to your own monitoring tools.

    Real-world example

    A small accounting firm could connect a tool server that ships its own skill for its invoice system, so the assistant knows the right steps without anyone writing them up. The firm could also use the new hook to stop any skill from quietly running shell commands on staff laptops.

    How you could use it

    If you already run an MCP server for your app or team, you could package your how-to instructions as a skill on that server so everyone who connects gets them. If you install skills from other people, you could set up the PreSkillShellCommand hook to block inline shell commands until you have reviewed them. Teams that track costs or behavior could pipe the new OpenTelemetry events into the dashboard they already use.

  2. OpenAI cuts GPT-6.2 usage: Astra hits limits 40% faster, Sol 25% faster

    OpenAI has reportedly tightened usage limits on GPT-6.2. According to the report, people on the Astra tier hit their cap 40% faster and people on the Sol tier hit it 25% faster than before. If your daily work or your app depends on these plans, you may run out partway through the day.

    Real-world example

    A freelance developer who uses GPT-6.2 for a full day of coding could find they hit the limit by mid-afternoon instead of at the end of the day, and lose a few hours of work time.

    How you could use it

    Check how close you already get to your cap and plan for less room. You could keep a second model or tool set up as a fallback for when you hit the limit. You could also save the strongest model for hard tasks and send routine jobs, like renaming or writing simple tests, to a cheaper option.

  3. pingdotgg/t3code T3 Code v0.1.12

    T3 Code v0.1.12 adds durable agent workflows in beta. These are multi-step jobs that keep going over time and can run on a schedule, and they pause for a human to approve before certain steps. The release also lets one project span several code repositories and links conversation threads across different machines.

    Real-world example

    A support team's developer could schedule a nightly workflow that has an agent draft fixes for new bug reports, then waits for a person to approve each one in the morning before anything is merged.

    How you could use it

    If you have chores you repeat by hand, like weekly dependency updates or cleanup across a frontend and a backend repository, you could set them up as a scheduled workflow. Add an approval step before anything risky, so the agent does the busywork and you keep the final say. Linked threads also help if you switch between a desktop and a laptop during the day.

Worth knowing

  1. Ask HN: Anthropic is accusing my company of distilling. How can I prove I'm not?

    One company posted that Anthropic accused it of distillation, which means using a model's answers to train a competing model. The company says it only runs automated regression benchmarks, which are repeated test runs that check whether quality has slipped. It was asking how to prove its innocence within 24 hours. This is one company's account, but it is a reminder that heavy, repetitive automated use of an API can look suspicious from the outside.

    Real-world example

    A small team building a chatbot for clinics could run the same few hundred test questions every night to catch quality drops. From the provider's side, that steady flood of scripted questions could look unusual.

    How you could use it

    If you run automated test suites against an AI provider, keep a short written note of what the tests are for, how often they run and how much traffic they send. Store test results in your own logs so you can show what you did if you are ever asked. Running fewer, smaller test sets also cuts cost.

Technique of the day

Verification before completion

Verification before completion means the assistant has to prove a task works before it is allowed to say it is done. You give it a skill, a saved set of instructions, that requires running the tests, the build or the app and showing the actual output. This stops the common problem of an AI cheerfully saying it fixed something that is still broken. It costs a little more time per task and saves a lot of time chasing false claims of done.

Try it

Create a skill file named verify-before-done with these instructions:
Before you say a task is complete, you must:
1. Run the project's tests and the build command.
2. Paste the real output, not a summary.
3. If anything fails, fix it and run again.
4. Only say done when the output shows success.
Never claim success without showing evidence.
